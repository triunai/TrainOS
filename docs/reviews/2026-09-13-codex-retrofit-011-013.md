## VERDICT: BLOCK

Two CRIT findings, both now **confirmed by live execution**, not just static reading:

1. **The action envelope's own external-effect pipeline is dead code in production.**
   `app.apply_effects` (011) writes every EXTERNAL effect as `DISPATCHED` and never calls
   `app.enqueue_effect_jobs` (012) — nothing does, anywhere outside the test pin. Confirmed by the
   orchestrator with a repo-wide grep: the only non-definition, non-comment call site is
   `supabase/tests/test_012_events_outbox_and_jobs.sql`. Every PROPOSAL_SEND / INVOICE_PUSH /
   REMINDER_SEND / BROADCAST_SEND action would dispatch and then simply never send anything, silently,
   forever. (Finding F2.)
2. **BYOK key rotation is permanently blocked on exactly the key that was just revealed** —
   i.e., the one case a security team would actually need to rotate a key. Reproduced live against the
   G6 shim: `ai_provider_key_set` → `ai_provider_key_reveal` → `ai_provider_key_rotate` on the same
   `provider_ref` raises
   `42501 REVEAL_AUDIT_REQUIRED: core.ai_provider_keys.last_revealed_at may only be written by the
   audited reveal path`. (Finding S1.)

Both are silent-failure or availability defects with no workaround inside the migration as authored.
Neither is exercised by the existing pins, which is why 13/13 and 14/14 "all pins pass" is true and
does not contradict either finding — see "Execution log" below for what the pins do and do not
exercise.

Independent of the two CRITs, there are three more HIGH findings that would each independently block
a real deployment (missing permission check on the whole HUMAN action-execution path; the
approval diff-hash guard being unable to ever detect a changed record; `bulk_decide`'s response shape
not matching what the web client's own contract type expects). See the findings table.

## 2 · The 7-point RPC contract check

**Point 1 (search_path pinned to `''`).** PASS, universally, verified independently three ways: both
reviewers' static reads, and the orchestrator's own live `pg_proc` query against the G6 shim (sampled
`app.claim_jobs`, `app.mint_agent_key`, `app.perform_action`, `core.perform_action` — all stored as the
exact single-element form `search_path=""`, no four-part list, no quoted-comma trap). 011 = 28/28,
012 = 31/31, 013 = 29/29 functions.

**Point 2 (definer identity never widened).** PASS. `SECURITY INVOKER` correctly used for both views
and pure validators/triggers that must not escalate. The one structural caveat — a `SECURITY DEFINER`
function reading its own forced-RLS table degrades to zero rows on a real (non-superuser) migration
owner — is acknowledged in-file by 013 and is unmeasurable in this harness (see "Could not verify").

**Point 3 (tenant isolation via `app.current_tenant_id()`).** PASS. Every client-reachable entry point
resolves tenant through `app.require_tenant_id()`; worker functions take an explicit, required
`p_tenant_id`. No policy predicate in any of the three packs reads a membership table inline. One named
exception, S1's sibling `app.report_effect_result`, addresses by `effect_id` alone with no tenant
predicate — acceptable only because it is `service_role`-only and reached solely from 012's
already-tenant-checked callers; worth naming explicitly in the header.

**Point 4 (envelope is `app.ok`/`app.err`, or the wrapper is named).** PASS — confirmed as a genuine,
intentional seam, not a defect. 011's three gate functions (`perform_action`, `decide_approval`,

explicitly documents this and prescribes the wrapper; 014 implements exactly that
(`core.perform_action`/`core.decide_approval`/`core.bulk_decide_approvals`, each `SELECT app.ok(app.<fn>(...))`).
013 is the first pack to call `app.ok()` directly. The catalog's own "011 calls neither" line is
accurate.

**Point 5 (REVOKE ALL FROM PUBLIC; client EXECUTE only where genuinely callable).** PASS for

Stays open.

**Point 6 (error codes match doc 09 / the migration header).** PASS for 011 (all `TRNOS`-coded raises

**Point 7 (every real call site matches args/order/types and envelope shape).** PASS for 011↔web

## 3 · Live-reproduced findings (orchestrator execution, not static reading)

### S1 — BYOK rotation deadlock, reproduced

Against the G6 shim (below), with a real tenant, membership, and AAL2-backed `auth.sessions` row:

```
ai_provider_key_set(...)     → success, key stored
ai_provider_key_reveal(...)  → success, {keyRef, auditId, revealedAt}
ai_provider_key_rotate(...)  → RAISES:
    sqlstate = 42501
    message  = core.ai_provider_keys.last_revealed_at may only be written by the
               audited reveal path (M-10): no app.key_reveal_audit row is named
               for this transaction
    detail   = {"code": "REVEAL_AUDIT_REQUIRED"}
```

This is deterministic and unconditional: **any** key, once revealed even once, can never be rotated
again through the public RPC surface. There is no time-based recovery (unlike the reveal ceiling,
which resets after 24 hours) — the only way out is a direct table edit disabling the trigger, which is
exactly the maintenance-hostile workaround `test_013`'s own T5 uses internally and which a real
operator does not have access to.

### T2/F2 — dead effect pipeline, confirmed by repo-wide grep

`grep -rn "enqueue_effect_jobs" --include="*.ts" --include="*.tsx" --include="*.sql" .` (excluding
