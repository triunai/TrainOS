# The app feels laggy — what was actually slow

13 Sep 2026. Reported: the blue RecordHeader card on `/approvals/APV-2026-0771`
(expand/collapse, hover) and clicking between rail items.

One cause, and it was neither of the two things that were suspected. The card is
not slow. The rail is not slow. Every read was sleeping.

## How this was measured

A private Chrome context on a dev server of its own (`:5181`), with the Vite HMR
socket blocked in the page so another lane saving a file could not reload the
tab mid-run. React commits counted through a `__REACT_DEVTOOLS_GLOBAL_HOOK__`
stub installed before React loads; long tasks, layout shifts and input latency
through `PerformanceObserver` (`longtask`, `layout-shift`, `event`).

**Two artefacts had to be removed before any number meant anything**, and both
had already produced wrong answers in this session:

- **A background tab is throttled.** With another lane's page in front, this one
  idled at 33.3ms per frame and every interaction measured 48ms. The same page
  in the foreground idles at 8.3ms and the same interaction measures 24ms. Every
  measurement below was taken with the tab brought to the front, and re-checked
  against `document.visibilityState`.
- **The machine is a 120Hz display.** A blank page in the same browser idles at
  8.3ms per frame, so 8.3ms is the floor here and not a slow frame. Judging
  against a 16.7ms budget would have cleared things that were not fine and
  flagged things that were.

## The cause

`FixtureClient` simulates a network round trip — `await sleep(this.#latencyMs)`
on every read — and its default is **120ms**. `apps/web` used the shared
singleton and so paid it on every read of every screen. Long enough to cross the
Suspense threshold, which is why the screen flashed `LoadingState` on the way in.

A/B on the live page, toggling `setLatency` on the singleton between runs and
clearing the query cache before each, first visit to each route:

| Rail destination | 120ms (before) | 0ms (after) |
| --- | --- | --- |
| `/training/engagements` | 158ms | 37ms |
| `/sales/enquiries` | 144ms | 37ms |
| `/knowledge/library` | 181ms | 30ms |
| `/sales/proposals` | 151ms | 32ms |
| `/training/trainers` | 412ms | 23ms |
| `LoadingState` flash | every one | none |

React was never the problem: 4–5 commits per navigation before and after, and
the longest frame during a navigation is 8.5–17ms either way.

The second visit to a route already cost ~20ms before the fix, because
`staleTime` is 30s and the cache answered. That is why the lag felt
intermittent rather than constant — it came back every time a screen went stale.

### The fix

`ApiProvider` sets the client's latency from `simulatedLatencyMs()`, which reads
`?latency=` and defaults to 0. The simulation is not deleted: it is how the
loading and error surfaces stay reachable by hand, so `?latency=120` restores
the client's own default and any other number is honoured. The client keeps
120ms as *its* default, because a fixture asked for one with no opinion should
still behave like a network.

Set in **render**, beside the sign-in, for the reason that comment already
gives: a child's `queryFn` fires from the child's mount effect, and a child
effect runs before a parent effect, so from an effect the first screen of every
session would still pay it.

Verified both ways in the browser: no flag → `latencyMs` 0 and a read returns in
0ms; `?latency=120` → `latencyMs` 120 and a read returns in 121ms.

## Cleared, with numbers

| Suspect | Verdict |
| --- | --- |
| Capture-phase scroll listener (`b397a54`) | **Clear.** 60 scroll frames: **0** React commits, median frame 8.4ms, **0** frames over 16ms. The class lands on exactly one element and no state moves. |
| Accent card — gradient, shadow, `transition` | **Clear.** Chevron click: 24ms end to end of which **1ms** is processing. A `pointerdown` that does nothing costs the same 24ms, so that is the pipeline floor, not the card. |
| Collapse height animation | **Clear.** Across two full expand/collapse cycles: median frame 8.3ms, max 9.3ms, **0** frames over 16ms. `grid-template-rows` is animating layout and is still paying for itself at 120Hz. No `will-change` or `contain` needed. |
| Card hover | **Clear.** Hovering across four controls: **0** React commits, no long tasks, 16–24ms input-to-paint. |
| `backdrop-blur` | **Not on this screen.** Only `Drawer` and `ProfileModal` use it. |
| Sidebar accordion animating on mount | **Clear.** The only animations in the first 1.5s of a load are the skeletons' `animate-pulse`. `useSidebarState` seeds `openKeys` from `localStorage` in the lazy initialiser, so the active group is already open at first paint. |
| React Query refetch storms | **Clear.** `staleTime` is 30s, not 0, and a navigation produces 4–5 commits total. |
| Lazy route chunks | **Clear, and this was the wrong guess.** A cold feature barrel imports in 7–23ms. Preloading the barrels by hand before navigating changed nothing — still 148ms, still a fallback — which is what ruled the chunks out and pointed at the data layer. No prefetch-on-hover is warranted. |

## Dev-only, not shipped, left alone

- One 57ms long task at ~100ms into every load: the bootstrap evaluating
  unbundled modules. A production build serves one chunk instead of a few
  hundred modules.
- `StrictMode` double-renders every component in development. It does not change
  the commit count (7 on load) and it is not in a production build.

## Still open

- `/sales/enquiries` is the one screen whose own render is visibly heavy: a
  62–83ms frame when its cache is cold, against 8.5–9.3ms for every other rail
  destination. Not the reported lag, and not touched here.
- `apps/web` tests: `finance.test.tsx` and `hrdc.test.tsx` each had one failure
  during this work. Both are in `InvoiceDetailScreen.tsx` and
  `ClaimPacketScreen.tsx`, which another lane had staged and modified at the
  time. Not from this change, which cannot affect a heading's name.
