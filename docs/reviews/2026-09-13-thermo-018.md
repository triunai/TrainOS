## Blockers

### B1 · One 4,857-line file holding five copies of the same list engine

`supabase/migrations/018_golden_path_rpcs.sql:1-4857`

The file goes from not existing to 4,857 lines. That alone is a presumptive
blocker, and the reason it is that long is not that there are thirty RPCs — it is
that the same code is written out five times.

`core.list_enquiries:781`, `core.list_approvals:2362`, `core.list_follow_ups:3055`,
`core.list_proposals:3332` and `core.list_quotations:3968` each open with the same
110-130 lines: page-size parse, cursor decode, saved-view merge, filter loop
against a `VALUES` whitelist, sort parse against a second `VALUES` whitelist,
`v_where` assembly, keyset append, count, the `jsonb_agg` + `row_number` page
query, the `next`-cursor rule, the `app.ok(data/page/appliedFilters)` return.

They are not similar. They are identical. Diffing the twenty-five lines from the
sort whitelist to the count in `list_proposals` against the same block in
`list_quotations`:

```
5c5
<                    ('value','value_sen'),('sentAt','sent_at'))
---
>                    ('sellPrice','sell_price_sen'),('version','version'))
19c19
<     'SELECT count(*)::integer FROM core.proposals WHERE tenant_id = $1 AND %s',
---
>     'SELECT count(*)::integer FROM core.quotations WHERE tenant_id = $1 AND %s',
```

Two lines differ out of twenty-five. The same holds for the page/cursor preamble
(`018:818-845` vs `018:3088-3115`) and for the `next`-cursor rule
(`018:1029`, `:2577`, `:3209`, `:3472`, `:4118` — five copies of one four-line
condition).

That duplication has already cost correctness twice, in opposite directions —
see H2 and H3. A defect fixed in one copy will not reach the other four, and the
divergence is invisible to review because the copies are 250 lines apart.

**The code-judo move.** Everything that varies between the five is data: a table
name, a filter whitelist, a sort whitelist, a default sort column, and a
projection expression. Everything that varies is already expressible as arguments
to the `format()` calls the file is making. One internal helper —
`app._list(p_relation text, p_filter_cols jsonb, p_sort_cols jsonb,
p_default_sort text, p_projection text, p_filter jsonb, p_sort text,
p_page jsonb, p_view text) RETURNS jsonb` — absorbs the whole preamble, the
where-assembly, the count, the keyset and the envelope. Each list RPC then
becomes its whitelists plus its projection, roughly thirty lines. That is about
500 lines deleted, five copies collapsed to one, and every one of H2, H3 and B3
becomes structurally impossible rather than individually fixed.

The same applies at smaller scale and is worth doing in the same pass:

- `(x.id::text = p_id OR x.ref = p_id)` appears **18 times**. One
  `app._resolve_ref()` predicate helper, or accept that it is a project idiom and
  say so once.
- `RETURN app.err('NOT_FOUND', jsonb_build_object('id', p_id))` appears
  **14 times** verbatim.
- `RAISE … USING ERRCODE = 'TRNOS', DETAIL = jsonb_build_object('code', …)::text`
  appears **30 times**. The `::text` round-trip of a jsonb bag through `DETAIL`
  is the kind of mechanism that should be written once,
  as `app._refuse(p_code text, p_details jsonb)`.
- The "requester has no app_role" preamble is copied **5 times**
  (`018:1798`, `:2083`, `:2974`, `:3681`, `:3796`).

### B2 · No catalog entry — the repo's own same-commit hard rule

`supabase/migrations/migration-catalog.md` is **not in the diff**, and the string
`018_golden_path_rpcs` does not appear in it.

`supabase/CLAUDE.md` states: *"Same-commit hard rule: any touch to
`supabase/migrations/` updates the catalog in the SAME commit. A catalog entry
that lands in a follow-up commit fails the gate."* It also defines four required
artifacts, of which the catalog Migration Order row and Detail section are one.
Three of four exist. This one does not. By the project's own rule the pack is not
reviewable until it does.

### B3 · Three list RPCs accept `p_view` and silently discard it

`supabase/migrations/018_golden_path_rpcs.sql:3059`, `:3336`, `:3972`

`core.list_follow_ups`, `core.list_proposals` and `core.list_quotations` all
declare `p_view text DEFAULT NULL` and never read the variable. I checked the
full body of each. `list_enquiries:846` and `list_approvals:2422` both implement
the saved-view merge; the other three do not.

**Concrete failing input:** `core.list_proposals(p_view => 'SV-MINE')` returns
*every* proposal in the tenant, with `appliedFilters: []`, `success: true`, and no
error. A reader who saved a view restricting them to their own proposals sees
everyone's.

This is the exact failure the file forbids in its own words at `018:869-872`:
*"FAIL CLOSED. An unrecognised field or op is `VALIDATION_FAILED` … never an
ignored clause: ignoring a filter shows rows the reader explicitly asked to
exclude."* An ignored **view** is an ignored filter. Either implement the merge
(it is the same twenty lines, which is B1's point) or drop the parameter from the
signature. Silently accepting it is the one option that is not available.

### B4 · 018 edits 014's pin so that 014 no longer passes on its own

`supabase/tests/test_014_rls_policies_and_client_grants.sql:229-249`

018 moves 014's exact grant-count assertion from `v_grants = 121` to
`v_grants = 124`, because 018 adds three view grants. The reasoning in the added
comment is sound and the exactness of the assertion is a good property.

The consequence is not. `test_014` is 014's pin. After this change, applying
001-014 and running `test_014` **fails**:

```
T1c FAIL: expected 124 SELECT grants in core to authenticated … Found 121.
```

A pin that only passes once a *later* migration has been applied is no longer
pinning its own migration, and the documented deploy order (014 before 018, per
`018:21-31`) guarantees a window where it is red. The three grants belong in an
018-owned assertion in `test_018`, with 014's count left alone or expressed as
`>= 121`.

### B5 · No transaction wrapper on a 4,857-line migration that also writes data

`grep -nE '^\s*(BEGIN|COMMIT)\s*;' supabase/migrations/018_golden_path_rpcs.sql`
returns nothing. Same for the rollback.

Every other migration in the band wraps: `014:177/949`, `015:148/312`,
`016:118/421`, `017:36/1340`, and their rollbacks at `014:47/208`, `015:26/84`,
`016:41/123`, `017:51/226`. 018 forward and 018 rollback are the only two files in
014-018 that do not.

This matters more here than elsewhere because 018 is not pure DDL. The backfill at
`018:4444-4462` loops every tenant writing `core.pipelines` and
`core.pipeline_steps` rows. Without a wrapper, a failure at line 4600 leaves
helpers created, some RPCs created, some not, and some tenants seeded.

It also disarms the rollback's own guard. The rollback's `$verify$` block raises
*"this rollback DESTROYED objects it does not own"* at
`supabase/rollbacks/018_golden_path_rpcs_rollback.sql:307` — but with no
transaction, the 47 drops it is complaining about have already committed
individually. A guard whose failure cannot undo what it detects is a report, not
a gate.

### B6 · The seed is not rollback-reversible, and R4 does not assert what it claims

`supabase/rollbacks/018_golden_path_rpcs_rollback.sql:217-226` and `:383-393`

The rollback drops the trigger and the two seed functions and **deliberately keeps
the seeded `core.pipelines` / `core.pipeline_steps` rows**. The stated reason at
`:217-223` is a good one — `core.engagement_step_states` carries composite foreign
keys onto those rows, and the seeds lane's fixtures share the derived ids, so
deleting them would take the fixture world with it.

The consequence is that **rolling back 018 does not restore the prior state**, and
cannot. `supabase/CLAUDE.md` requires the rollback to reproduce the prior
definition in full. Here the prior *data* state is unreachable by design: once the
rollback has run the mechanism is gone, so there is no longer any supported way to
undo the seed at all. Concretely, `pipelines_one_default_uq` — the partial unique
index on `(tenant_id, object) WHERE is_default` — still rejects a default
`ENGAGEMENT` pipeline for every tenant after the rollback. The 008 and 009 fixtures
this PR had to edit (`test_008:112-118`, `test_009:374-377`) stay broken in their
original form. A rollback that leaves a repo-wide constraint change permanently in
place is not a rollback, and that is the strongest argument that M4 is right: the
seed belongs in its own provisioning migration, where its irreversibility is the
subject of review rather than a footnote in an RPC pack.

**The assertion meant to cover this does not exist.** `:224` states *"What goes is
the MECHANISM; what stays is the DATA, and R4 asserts exactly that."* R4's own
comment at `:383-387` repeats it: *"and so are the pipeline rows themselves."*
R4's actual body (`:389-393`) queries `pg_trigger` for **016's**
`trg_tenants_seed_ref_formats` and nothing else. It never reads `core.pipelines`
or `core.pipeline_steps`. Two comments and the closing `RAISE NOTICE` at `:395-397`
all announce a check that was never written — the same overclaiming pattern as H1
and H5.

## High

### H1 · `core.regenerate_proposal_section` enqueues nothing, and says it does

`supabase/migrations/018_golden_path_rpcs.sql:3915-3941`

The comment reads: *"What it does is ENQUEUE the work through 011's own envelope
and hand back the run the worker will fill."*

The code does not enqueue anything. It inserts one `core.runs` row with
`status = 'RUNNING'`, flips `needs_review` on the section, and returns the run id.
There is no call to `app.perform_action`, `app.emit_event`,
`app.enqueue_effect_jobs` or the outbox anywhere in 018 — `grep` for all four
across the file returns only comments and the verify block. And there is no
trigger on `core.runs`: 013 defines ten indexes on it (`013:1632-1648`) and no
`AFTER INSERT`.

**Concrete behaviour:** pressing "Regenerate" writes a `RUNNING` run that nothing
will ever complete, marks the section as needing review, and returns 200. Press it
five times and the tenant has five orphan `RUNNING` runs. Nothing in the product
ever regenerates the section.

`test_018:1768` (T26p) asserts only that two consecutive calls return *different*
`runId`s, so the pin locks the inert behaviour in rather than catching it. Either
wire the enqueue or return a refusal saying the worker path is not deployed. The
comment must not describe a mechanism that is absent.

### H2 · `list_enquiries` counts after the cursor clause, so `page.total` shrinks

`supabase/migrations/018_golden_path_rpcs.sql:944-952`

The keyset predicate is appended to `v_where` at `:944-948`, and the total is
counted at `:950-952` **using that same `v_where`**. So `page.total` is the number
of rows *after* the cursor, not the number matching the filter.

The other four list RPCs count first and append second: `list_approvals` counts at
`:2494` and appends at `:2513`; `list_follow_ups` `:3169` then `:3174`;
`list_proposals` `:3441` then `:3446`; `list_quotations` `:4087` then `:4092`.
`list_enquiries` is the only one of the five in this order. This is the
copy-paste divergence B1 predicts.

**Concrete failing input:** 120 enquiries matching the filter, `size: 50`.
Page 1 returns `page.total: 120`. Page 2 returns `page.total: 70`. Page 3 returns
`page.total: 20`. The list header counts down as the reader pages.

`test_018:417` (T4a) asserts `page.total = 3` on the **first** page only. T4e
checks page 2's row count and never re-reads `page.total`, so the pin does not
catch it.

### H3 · The other four hand back a cursor past the end on an exact-multiple page

`018:2577`, `:3209`, `:3472`, `:4118`

With `v_total` holding the full filtered count, the terminating condition
`IF v_count = v_size AND v_count < v_total` is wrong on the last full page.

**Concrete failing input:** exactly 100 matching proposals, `size: 50`. Page 2
returns 50 rows with `v_total = 100`, so `50 < 100` holds and `page.next` is a
non-null cursor pointing past the last row. The client fetches page 3 and gets
`data: []`, `next: null`. One wasted round trip and an empty render on every
exact multiple of the page size.

`list_enquiries` does *not* have this bug, because its `v_total` is the remaining
count — the two defects are the same copy-paste error cancelling in one copy and
not in the other four. The correct test is on the count alone, after fetching
`v_size + 1` rows and trimming, which is the standard keyset shape and which the
single `app._list` helper from B1 would implement once.

### H4 · `put_quotation` rewrites the tax treatment on every call, including an empty body

`supabase/migrations/018_golden_path_rpcs.sql:2237-2261`

The `app.resolve_tax_policy(v_tenant, 'CORPORATE_TRAINING')` lookup and the
`UPDATE core.quotations SET sst_policy_id, sst_rate, sst_reason,
sst_exempt_reason` that follows it are **unconditional**. They are outside the
`IF p_body ? 'lines'` guard and outside the `IF p_body ? 'sellPrice'` guard.

`p_body` is coalesced to `'{}'` at `:2123`. So `core.put_quotation(id, '{}')` —
a body with no lines, no price, nothing — performs a tax rewrite and nothing else.

Two consequences:

1. **The category is hardcoded.** 017 seeds two policies; this writer can only ever
   select `CORPORATE_TRAINING`. The file’s own comment at `:2224-2232` admits it:
   *"Choosing the exempt one requires knowing the BUYER is an Education Act
   institution, and no column in 001-017 records that."* Any quotation that is
   ever set to `TRAINING_EXEMPT` by another path is silently reset to
   `STANDARD_RATED` at 8% on the next save, and `sst_sen` / `gross_price_sen` are
   `GENERATED` from `sell_price_sen * sst_rate`, so the customer-facing gross
   changes. Latent today because no other writer sets the exempt policy; a
   trap the moment one does.
2. **A no-op PUT is a write.** It bumps `updated_at` and fires 007's triggers on a
   request that changed nothing.

Doc 09 §14.8 as amended by this PR says the fix is *"a trigger on
`core.quotations`, or the same resolution in every writer."* The trigger is the
right half of that disjunction: it puts the rule where the column lives, makes it
unconditional-by-construction rather than unconditional-by-accident, and takes
28 lines out of an already 311-line function.

### H5 · The pin does not hold — about thirty assertions cannot fail

`supabase/tests/test_018_golden_path_rpcs.sql`

The file has 239 labelled `RAISE EXCEPTION` assertions and zero `ASSERT`
statements. (The brief said 228; that number is 014's RLS policy count at
`migration-catalog.md:219`, not an assertion count for this file.) A material
fraction of them cannot fail.

**Four are provably unfalsifiable:**

- `:1540` (T23g) — `IF v_q.gross_price_sen <> v_q.sell_price_sen + v_q.sst_sen`.
  `017:604-610` defines `gross_price_sen` as
  `GENERATED ALWAYS AS (sell_price_sen + round_half_up_sen(sell_price_sen * sst_rate))`
  and `sst_sen` as the second term. The assertion reads `x <> x`.
- `:1950` (T30d) — compares the `id` of two distinct `core.pipeline_steps` rows for
  equality. `id` is the primary key (`004:639`), so two distinct rows can never
  share one. The comment two lines above already explains that the real failure
  aborts at the seed with a PK violation, before this line runs.
- `:1031` (T14e) — checks `code = 'POLICY_APPROVAL_REQUIRED'` on a path
  `:1014` has already restricted to `code = 'FLOOR_PRICE_BREACH'`.
- `:953` (T13i) — filters the fixture's lines for `item ILIKE '%pax%'`. The
  fixture's only two lines are `"Trainer days"` and `"Materials"`. The count is
  unconditionally zero.

**About thirty more pass vacuously on a refusal.** The idiom
`d := core.get_x(…) -> 'data'; IF d ->> 'k' <> 'v' THEN RAISE` evaluates to `NULL`
when the RPC returned `{success:false,…}`, and `IF NULL` takes the false branch.
Fifteen blocks extract `-> 'data'` without first asserting `success`, including
`:626`, `:631`, `:762`, `:777`, `:1102`, `:1346`, `:1367`, `:1655`, `:1694`,
`:1736`, `:1768`, `:1790`. Every assertion downstream of each reports pass if the
RPC refused. The correct pattern is already used elsewhere in the same file
(`:414`, `:526`, `:602`, `:919`, `:1623`, `:1781`, `:1828`) — it just is not used
consistently.

**Coverage gaps.** `core.get_proposal` (`018:1707`) and `core.get_quotation`
(`018:1952`) are **never invoked** by the pin — they appear only in comments and in
T17's metadata sweep, so their projections, their `NOT_FOUND` paths and their
envelopes are entirely unasserted. `core.get_compliance_rule` is only ever called
with a deliberately absent id, so no `ComplianceRule` payload is ever projected.
`core.get_audit` is only exercised against a record with an empty trail.
`core.badge_counts` asserts the three key names and `jsonb_typeof = 'number'` but
never a count value, so a badge returning a constant zero passes.

Three assertion comments also overclaim: `:575` says the two refusals are
"BYTE-IDENTICAL" and compares only `error.code`; `:1389` banners "EVERY RPC" and
probes 18 of 30 for envelope shape only; `:1733` announces a provenance check that
was never written.

## Medium

### M1 · `core.provenance` is read without a tenant predicate, twice

`018:230` (inside `app._provenance`) and `018:2669` (inside `core.get_approval`)
both filter on `subject_table` and `subject_id` only. Every other read in the file
is tenant-correlated; I checked all of them.

This is **not reachable as a cross-tenant leak today**: `subject_id` is always a
uuid from a row the caller's tenant already owns, and 014 grants `authenticated`
no write privilege anywhere in `core`, so no caller can plant a provenance row
with a chosen `subject_id`. It is still wrong for two reasons. It breaks the
posture the file states at `018:61-63`, and it defeats the index —
014's verify check 10 requires `tenant_id` to lead an index on every core table,
so a lookup without `tenant_id` cannot use it, on what will become one of the
largest tables in the system.

`018:2669` has a second problem: `LIMIT 1` with **no `ORDER BY`**. If more than one
provenance row exists for an approval, which `jury` becomes `modelAgreement` is
whatever the planner returns. `app._provenance:236` gets this right with
`ORDER BY prov.updated_at DESC LIMIT 1`.

### M2 · `core.me` reports the membership role; every gate enforces the JWT role

`018:539` refuses when `v_actor.role` (from `app.current_actor()`, i.e. the JWT)
is null, but `018:583` returns `v_member.role` (from `public.memberships`), and
`018:578` derives the whole `permissions` list from `v_member.role`.

Two sources of truth for one concept. If a JWT is stale relative to the
membership row, the shell renders one role's affordances and the server enforces
another's. Pick one — the membership row is the better answer — and make
`app.current_actor()` the thing that reads it, so the divergence cannot exist.

### M3 · `IDEMPOTENT_REPLAY` carries two different meanings with nothing to tell them apart

`018:1854` (key reused with a different body — permanent, do not retry) and
`018:1865` (a request with this key is still in flight — transient, retry shortly)
raise the identical detail bag `{'code':'IDEMPOTENT_REPLAY'}`. `018:2112` is a
third use of the same code.

A client cannot distinguish "your request conflicts" from "wait a moment". Add a
`reason` key to the bag.

### M4 · A provisioning trigger and a cross-tenant backfill do not belong in an RPC pack

`018:4317-4462` adds `app.seed_pipelines(uuid)`, `app.seed_pipelines_on_tenant()`,
the `trg_tenants_z_seed_pipelines` trigger on `public.tenants`, and a `DO` block
that loops every existing tenant writing rows into `core.pipelines` and
`core.pipeline_steps`.

The file's own header says: *"It creates no table and no enum value"* and
*"No existing table, function, view, policy or grant is modified."* Both are
true and both miss the point — it modifies existing **data**, across every tenant,
from a migration whose stated subject is read and write RPCs.

The blast radius is already visible in the PR: 008's and 009's pins had to be
edited (`test_008:112-118`, `test_009:374-377`) because a seeded default
`ENGAGEMENT` pipeline now collides with `pipelines_one_default_uq`. Every future
fixture that inserts a default engagement pipeline will hit the same wall. That is
a repo-wide semantic change introduced as a subsection of an RPC file. It belongs
in a provisioning migration of its own, beside 016's ref formats and 017's check
keys, where it can be reviewed and rolled back as one thing.

(The 009 edit also papers over a pre-existing defect worth its own ticket: the
`INSERT INTO core.engagements … FROM core.programmes p, core.pipelines pl` at
`test_009:389` is an unconstrained cross join whose `RETURNING … INTO` kept an
arbitrary row the moment the tenant had more than one pipeline.)

### M5 · The backfill swallows a foreign-key violation and reports success

`018:4453-4456`

```sql
EXCEPTION WHEN foreign_key_violation THEN
  RAISE WARNING '018 backfill: tenant % has no PIP ref_format; pipelines not seeded.', v_tenant;
```

A tenant that predates 016's backfill is skipped and the migration completes
green. Because `core.navigation:596` and `core.get_pipeline_config:2714` render
stages from `core.pipeline_steps`, that tenant's navigation comes back with an
empty stage list — a silent, correct-looking empty rather than an error. A
`WARNING` in a migration log is not a channel anyone reads later. Either fail the
migration and make the operator fix the ref format first, or collect the skipped
tenant ids and raise once at the end with the list.

### M6 · The header's write/read split is factually wrong, and the rule is applied inconsistently

`018:72-80` states the refusal rule and enumerates *"WRITE functions
(`create_proposal`, `put_quotation`)"*.

Six RPCs write: those two plus `core.patch_enquiry_extraction:2955`,
`core.add_proposal_section:3659`, `core.put_proposal_section:3775` and
`core.regenerate_proposal_section:3865`. The first three of those four use
`RAISE … TRNOS` as the rule requires. `regenerate_proposal_section` uses
`app.err` at `:3885`, `:3893`, `:3903` and `:3913` — which **commits**.

Those four refusals happen to be computed before its first write, so nothing
partial escapes today. But the rule exists precisely so that nobody has to verify
that by hand for each new branch, and the next edit to that function breaks it
silently. Fix the header's enumeration and move `regenerate_proposal_section` onto
the same mechanism as the other five writers.

### M7 · `put_quotation` derives line numbers two different ways over two scans

`018:2139` counts `v_n := v_n + 1` while validating; `018:2176` assigns
`n` as `(row_number() OVER ())::smallint` in a separate `INSERT … SELECT` over the
same array, with no `ORDER BY` in the window.

So the `lines[N]` index quoted back in a validation error and the `n` actually
stored are produced by two independent mechanisms that happen to agree because
`jsonb_array_elements` preserves order. One `jsonb_array_elements(…) WITH
ORDINALITY AS element(value, n)` drives both, and the validation can then be a
`WHERE` clause on the same statement rather than a preceding loop.

### M8 · Three test refusal-paths accept any `TRNOS` error, not the intended one

`test_018:1596-1600`, `:1727-1731`, `:1745-1749` end in
`EXCEPTION WHEN sqlstate 'TRNOS' THEN NULL;` without reading
`PG_EXCEPTION_DETAIL`. A `NOT_FOUND` or `FORBIDDEN` passes a test written for
`VALIDATION_FAILED`. The same file does it correctly at `:825`, `:867`, `:879`,
`:970` and `:1012`.

## What is right, and should not be lost in a rewrite

- **Tenant scoping is disciplined.** I checked every `JOIN` and every
  `FROM core.*` / `FROM public.*` in the file. Every join is tenant-correlated
  (`018:1012`, `:1148`, `:1454`, `:1667`, `:2843`, `:2889`, `:3538` all carry
  `x.tenant_id = y.tenant_id`), and every table read filters on
  `app.require_tenant_id()`. M1 is the sole exception and it is not reachable.
- **No error is swallowed into `app.ok`.** I traced all 18 `EXCEPTION` handlers.
  Every one either re-raises, returns `app.err`, or (at `018:551-556`) sets a
  variable that leads to an explicit `FORBIDDEN` two branches later. The one
  swallow is M5, and it is in a `DO` block, not an RPC.
- **The rollback is inventory-correct on objects** (its data contract is a
  separate matter — see B6). All 47 created objects are dropped, every
  signature matches, nothing from 001-017 is destroyed, drop order is exact
  reverse dependency order, and there is no `CASCADE`. The one drop of a
  non-018 object — `core.decide_approval(uuid,text,text,text)` at
  `…_rollback.sql:209` — is signature-qualified and cannot touch 014's five-argument
  function at `014:666`. That is the right call and it is correctly explained.
- **Yielding the three gate wrappers to 014** (`018:465-513`) rather than shipping
  a second copy is exactly the divergence discipline `CLAUDE.md` asks for, and
  keeping the *assertions* while dropping the code is the right instinct.
- **The §14 divergence appendix** added to `docs/architecture/09-golden-path-rpc-specs.md`
  is additive and names ten real spec defects with fixes. Amending the spec
  alongside the implementation is usually a smell; recording divergences in a
  separate numbered section is the exception, and it is done well here.
- **`app.round_half_up_sen` is respected.** No money is computed in the RPC layer;
  `put_quotation` writes lines and reads back 007's generated columns. The 311-line
  function is too long, but it is long for the right reason.
