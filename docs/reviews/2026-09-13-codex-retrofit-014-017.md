  DROP POLICY." A future migration reusing that naming convention would have its policies
  silently dropped by 014's rollback.
- **MED (Codex only):** a **future** conflict, out of this PR's scope but worth recording —
  Codex found a commit on another lane's history (`rpc-018`, not part of this PR)
  defining a four-argument `core.decide_approval`, while 014 defines a five-argument version.
  If both land, `CREATE OR REPLACE FUNCTION` creates a sibling overload (PGRST203 risk). Not a
  defect in this PR; flagged for whoever picks up 018 next.
- **LOW (repo's own `check:grants` guard, surfaced on push, not by either reviewer):**
  `supabase/tests/test_014_rls_policies_and_client_grants.sql:513` defines a `SECURITY DEFINER`
  function inside the test transaction (`pg_temp.t014_read_approvals()`, used for T7 to simulate
  the definer-read path into `core.v_approval_requests`). The guard's rule is "a test must not be
  able to create the privilege escalation it is supposed to be checking for." This one lives in
  `pg_temp` (session-local, dropped when the pin's transaction rolls back) so it cannot actually
  escalate anything outside the test — most likely a false positive against a rule that doesn't
  yet special-case `pg_temp`. Flagged rather than dismissed: worth a one-line allowlist/exception
  in `scripts/check-grants.mjs` for `pg_temp.*` so the guard stops firing here, or worth confirming
  the harness-function pattern really can't be reached by anything outside the transaction.
- **INFO (security pass):** positively verified and NOT a finding — the tenant-nullable fallback

  predicate correctly InitPlan-wraps `(SELECT app.require_tenant_id())`, all three wrappers carry
