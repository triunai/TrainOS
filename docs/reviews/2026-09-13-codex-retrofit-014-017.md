## Answering the standing CI question: does `check:grants` need a test-file exemption?

**Verdict: `check:grants` needs the exemption, not the test.** The finding
(`supabase/tests/test_014_rls_policies_and_client_grants.sql:513`, a `SECURITY DEFINER` function)
is a **false positive**. The function is created as `pg_temp.t014_read_approvals()` — session-local
temp-schema, dropped automatically when the pin's transaction rolls back at end of file. It cannot
be called, referenced, or reached by anything outside that one transaction, so it cannot manufacture
the privilege escalation the guard exists to catch; it exists only to simulate, inside the pin, the
same definer-read path `core.list_approvals` will use in migration 018. Removing the pattern would
remove the only test of `core.v_approval_requests`'s deliberately-not-granted posture (see 014
finding #9 below), which is a real and valuable check. **Recommendation:** add a one-line exemption
to `scripts/check-grants.mjs` for functions created in `pg_temp` (or matching `pg_temp\.`), since a
`pg_temp` object is architecturally incapable of persisting the escalation the rule is guarding
against. Do not change the test.

## Pin-edit audit — the nine (ten, counting `test_004` twice) earlier packs' pins amended by this lane

Diff `826bb52..52caf6b` over `supabase/tests/`: **10 files, 14 diff hunks** (not quite the "nineteen"
named in the brief — recounted twice, independently, by both this orchestrator and the security
pass, with the same number both times; the discrepancy is most likely a difference in what's being
counted, e.g. individual `SET`-clause lines inside the `ON CONFLICT` blocks, rather than a
missed edit).

**Verdict: all fourteen are legitimate fixes. None is a weakened assertion.**

- **Eleven `ON CONFLICT (tenant_id, prefix) DO UPDATE` additions** (across `test_004` ×2, `test_005`,
  `test_006`, `test_007`, `test_008`, `test_009`, `test_010`, `test_011`, `test_013`, `test_014`),
  made necessary because 016 now auto-provisions every tenant's `ref_formats` via trigger, which
  collides with these pins' own fixture INSERTs. Independently verified (security pass): every one
  sets the `DO UPDATE` clause from `EXCLUDED.*` on exactly the same columns the plain INSERT set, so
  the post-statement row is byte-identical to the pre-016 result regardless of what the trigger
  seeded first. No value can silently drift on a re-run.
- **One fixture addition** (`test_006`, `hrd_tdf_valid_to = CURRENT_DATE + 400` on two trainer rows),
  made necessary by 017's new accreditation-expiry constraint. Legitimate — the fixture needs those
  two trainers to remain "accredited" for the rest of the pin, and a future date does that.
- **Two recomputed counts** (`test_014` T1a `113→116`, T1c `116→121`), to account for 017's three new
  tenant-scoped tables and two new granted views. Both **independently recounted from the DDL and
  confirmed correct** by the security pass, and both independently re-derived by direct SQL
  execution (G6: `v_pairs = 116`, `v_grants = 121`, matching exactly).

**Two secondary observations, not defects in the edits themselves:**
1. The eleven `ON CONFLICT` edits make the ten earlier pins structurally blind to 016 being broken —
   if 016's trigger silently seeded nothing, `DO UPDATE` would insert the fixture row anyway and
   every downstream assertion in those ten files would still pass. `test_016` is the only pin that
   actually covers 016; this is a coverage gap worth naming, not a regression in the edited files.
2. `test_014`'s two recomputed counts now couple that pin to 017's schema — it can no longer be run
   standalone against a database at exactly migration 014, and a bisect of 017 would make `test_014`
   fail with a message that (correctly, but confusingly) blames counts that look like they're about
   014. Consider deriving the expected counts from `to_regclass(...)` checks rather than a hardcoded
   post-017 literal.
3. **Found separately during G6 execution, not in the diff**: `test_014`'s own success `RAISE NOTICE`
   text (line 271-272) still prints the **pre-017 numbers** ("113 tenant policy pairs... 118 SELECT
   grants") even though the assertions above it were correctly updated to 116/121 — the pin passes
   while printing two numbers that are each 3 low. Cosmetic (the `ASSERT`s are what actually gate
   pass/fail), but anyone reading the pin's own console output as evidence gets stale figures.
