## Findings — migration 016 (tenant provisioning, including the `564dd64` amendment)

**Verdict: BLOCK — on the rollback specifically; the forward migration and the `564dd64` amendment
are both sound.** Both reviewers independently verified the original pack's central mechanism is
real: `core.ref_formats` seeding is genuinely derived from `pg_trigger` (every trigger whose
function is `core.assign_ref`, reading its prefix argument), not a hardcoded list — 32 prefixes,
confirmed by direct execution: a fresh tenant is auto-provisioned exactly 32 rows.

### The `564dd64` amendment — reviewed separately, no new findings

`app.provision_tenant` gains a fourth parameter, `p_id uuid DEFAULT NULL`, so the seeds lane (PR
#16) can provision a tenant under a fixed, memorable id instead of a generated one — needed because
`ref_formats`/`action_policies`/`check_keys` already reference the tenant by the time the function
returns, and none of those foreign keys is `ON UPDATE CASCADE`, so a generated id cannot be
retrofitted after the fact. Verified directly:

- **The `DROP FUNCTION IF EXISTS app.provision_tenant(text,text,text)` before the new
  `CREATE OR REPLACE`** is present and correctly ordered — a bare `CREATE OR REPLACE` with a
  changed parameter list creates a second overload rather than replacing the function, which the
  commit message's own claim ("both would then carry defaults... every existing caller would fail
  with 'is not unique'") is the right mechanism to worry about. The DROP is exactly the fix.
- **No other call site exists anywhere in the repository** (`apps/`, `packages/`, other
  migrations) — grep for `provision_tenant` returns matches only inside 016's own migration,
  rollback, test, and the catalog. The function is "not granted to any client role... an operator
  act," so there's no PostgREST/RPC exposure to break either.
- **The rollback drops both signatures** (`app.provision_tenant(text,text,text,uuid)` then
  `(text,text,text)`), correctly anticipating that a database rolled back and forward around the
  amendment boundary could carry either — this is the right defensive pattern and is exactly what
  016's own original rollback (finding #1 below) should have done for `ref_formats` ownership but
  didn't.
- **The four new T3 assertions are real, not decorative**: explicit id is honored on both the
  returned value and the stored row (T3e/T3e2); supplying an id does not bypass provisioning — the
  tenant still gets all 32 `ref_formats` rows (T3e3); explicit `NULL` still generates an id (T3f);
  a duplicate id is refused by the primary key rather than silently reattaching a new customer to
  another customer's rows (T3g).

This amendment is a clean, narrowly-scoped, well-tested fix. **No finding.**

## Thermonuclear review (maintainability/abstraction) — a genuine pass, not the substitute

While this report was being drafted, `.claude/skills/thermo-nuclear-code-quality-review/SKILL.md`
appeared in this environment for the first time (it did not exist when the earlier substitute pass
ran, and does not exist anywhere else in the repo's history). A real thermonuclear pass was
dispatched against 015/016/017 immediately, applying the skill's own methodology directly rather
than a substitute. This satisfies G5's "both must land" requirement in full for this pass, on top
of the security substitute already run — three independent lenses total on 015/016/017.

**Verdicts from this lens: 015 approve-with-one-change, 016 approve-with-changes, 017 BLOCK
(structural decomposition), consistent with this report's own verdicts above.**

- **017's 1340-line single transaction is a maintainability blocker independent of its already-found
  correctness issues.** Its twelve sections (grant sweep, jsonb CHECKs, numeric precisions, three
  new tables, SST, PDPA, HRD, retrieval RPC) hold the *union* of every touched table's ACCESS
  EXCLUSIVE lock for the whole run and force an all-or-nothing rollback — which is exactly why the
  rollback re-opens the nine PUBLIC-EXECUTE grants "deliberately": reverting the SST design and
  reverting the security fix are welded together by the file boundary, not by necessity. Recommended
  split into independently-reviewable, independently-rollback-able pieces (grants / new tables /
  SST / PDPA / HRD / retrieval).
- **A real, functional finding, not just style — added to 017's findings table below as #19.** 017
  adds a third tenant-provisioning trigger (`app.seed_compliance_check_keys`, mirroring 016's
  `seed_ref_formats` pattern almost line-for-line) but never updates `app.provision_tenant`'s
  completeness guard (`016:279`, already flagged above for checking `v_formats = 0` rather than an
  exact count) to also verify check-keys were seeded. The exact failure mode 016's own guard exists
  to catch — "refuse to hand back a tenant that looks provisioned but is missing something a ref'd
  table needs" — is now unguarded for the newest seed. This is the concrete cost of copy-pasting the
  seed-trigger pattern three times (011, 016, 017) instead of extracting one registry-driven
  `app.seed_tenant()`.
- **The `ADD CONSTRAINT` NOT VALID/VALIDATE convention is named as a known trap three times in this
  repo's history (004, 014, 017's own header) and hand-applied inconsistently within 017 itself** —
  six of fifteen constraint-adds in 017 use a plain `ADD CONSTRAINT` where the file's own stated
  rule calls for the guarded form. A rule stated in prose three times and enforced by hand is exactly
  the kind of drift the gate's postmortems are about. Recommended: extract one
  `app.add_constraint(schema, table, name, definition, validate)` helper into 004 so the lock choice
  becomes a visible argument instead of a convention someone has to remember.
- **015 is the cleanest of the three** — one small fix recommended (drive the cron job's registered
  command from a typed `regprocedure` cast rather than regex-parsing it back out in the verify
  block, which eliminates a branch rather than just tidying it).
- Smaller cross-cutting notes: `SET LOCAL lock_timeout='5s'`, present in every migration 001-013,
  is silently absent from 014-017's files — worth confirming this is deliberate rather than a
  dropped convention, in the pack's most lock-dangerous stretch. Multiple pin files duplicate the
  same tiny harness helpers (`pg_temp.t0NN_try`) that could be one shared `tests/_harness.sql`.

None of this changes any pack's verdict — 017 was already BLOCK on security grounds, 015 and 016
were already MERGE-WITH-FIXES/BLOCK respectively for reasons independent of these — but it
substantiates 017's BLOCK from a second, disjoint angle, which is the concrete case this skill's own
"two reviewers reliably find disjoint problems" argument makes.

## Pin-edit audit — diffed against `origin/main`

As noted above, diffing `supabase/tests/` against `origin/main` today produces the same result as
diffing against 014's own tip, because `main` unexpectedly carries 014's content. The result:
**10 files, 14 diff hunks** for the nine earlier packs (`test_004` through `test_014`, `test_004`
touched twice) — not the "nineteen" named in the brief. This was independently recounted from two
different diff bases (014's tip, and now `origin/main`) with the same number both times.

**Verdict: all fourteen are legitimate fixes. None is a weakened assertion.**

- **Eleven `ON CONFLICT (tenant_id, prefix) DO UPDATE` additions** (across `test_004` ×2,
  `test_005`, `test_006`, `test_007`, `test_008`, `test_009`, `test_010`, `test_011`, `test_013`,
  `test_014`), made necessary because 016 now auto-provisions every tenant's `ref_formats` via
  trigger, colliding with these pins' own fixture INSERTs. Independently verified: every one sets
  the `DO UPDATE` clause from `EXCLUDED.*` on exactly the same columns the plain INSERT set, so the
  post-statement row is byte-identical to the pre-016 result regardless of what the trigger seeded
  first. No value can silently drift on a re-run.
- **One fixture addition** (`test_006`, `hrd_tdf_valid_to = CURRENT_DATE + 400` on two trainer
  rows), made necessary by 017's new accreditation-expiry constraint. Legitimate.
- **Two recomputed counts** (`test_014` T1a `113→116`, T1c `116→121`), to account for 017's three
  new tenant-scoped tables and two new granted views. Both independently recounted from the DDL and
  confirmed correct, and both independently re-derived by direct SQL execution in the earlier G6
  pass (`v_pairs = 116`, `v_grants = 121`, matching exactly).

**Secondary observations, not defects in the edits themselves:**
1. The eleven `ON CONFLICT` edits make the ten earlier pins structurally blind to 016 being broken
   — if 016's trigger silently seeded nothing, `DO UPDATE` would insert the fixture row anyway and
   downstream assertions would still pass. `test_016` is the only pin that actually covers 016.
2. `test_014`'s two recomputed counts couple that pin to 017's schema — it can no longer be run
   standalone against a database at exactly migration 014. Consider deriving the expected counts
   from `to_regclass(...)` checks rather than a hardcoded post-017 literal.
3. `test_014`'s own success `RAISE NOTICE` text still prints the pre-017 numbers ("113 tenant
   policy pairs... 118 SELECT grants") even though the assertions above it were correctly updated
   to 116/121 — cosmetic (the `ASSERT`s gate pass/fail), but misleading if read as evidence.
