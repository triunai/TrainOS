## Checks

**1. All 23 gates.** Every one of the 25 `CREATE OR REPLACE FUNCTION core.*` bodies in 021 (badge_counts + get_audit + 23 gated RPCs) was extracted and its DECLARE/first-statement checked: the DECLARE section holds only literals and `app.require_tenant_id()`, and the first executable statement in every one of the 23 is the `-- 021 · AUTHZ FIRST` comment immediately followed by `IF NOT app.has_permission(...)`. All 20 distinct permission strings used (`enquiry:read`, `enquiry:edit_extraction`, `followup:read`, `organisation:read`, `opportunity:read`, `contact:read`, `tna:read`, `proposal:write/read/regenerate`, `quotation:read/write`, `policy:read`, `pipeline:read`, `programme:read`, `compliance:rule:read`, `audit:read`, `approval:read`) exist verbatim as `role_permissions` rows in 002 §11. The migration's own `$verify$` V2 structurally re-asserts gate-before-read for all 27 client-callable RPCs (string-position check of `app.has_permission(` vs `FROM core.`/`FROM app.` in `pg_proc` source), and V1 asserts SECURITY DEFINER, `search_path=""`, `statement_timeout=10s`, and the authenticated-only/no-anon grant, off `pg_proc`/`has_function_privilege` — not from DDL text.

No un-gated overload: every one of the 25 replaced functions has exactly one definition in `pg_proc` after the build (V1), and a byte-for-byte signature diff against 018 confirms `CREATE OR REPLACE` is a true replace, not a new overload, for every multi-argument function (`list_enquiries`, `list_follow_ups`, `list_proposals`, `create_proposal`, `add_proposal_section`, `put_proposal_section`, `put_quotation`) and every single-line-signature one. No bypass view: the only internal callers of the gated RPCs are 018's own writer-returns-through-reader pattern (`create_proposal`/`add_proposal_section`/`put_proposal_section`/`put_quotation` calling `get_proposal`/`get_quotation` at the end, `list_proposals`/`list_quotations` projecting rows through the same function) — those re-check the same actor's permission, they don't skip it, and `$verify$` V3 asserts every role holding a write permission also holds its reader's permission so the composition can't dead-end into an unreachable-but-should-work write. `get_audit`'s second gate (`approval:read` for the approval-trail branch) is decided before the `approval_requests` lookup it guards (021:226-231, "Decided before the lookup" — confirmed by reading, not just the comment).

**2. Amended pins.** `test_011` T1b/T1c and `test_012` T1p move the action-type/policy count 22→23, matching R18's one new `app.action_types` row and its per-tenant OPP-01 seed — arithmetic, not behavior, and the underlying 22 assertions are untouched. `test_018` T19g now accepts `FORBIDDEN` (was presumably `NOT_FOUND`-only) for an unknown compliance rule read as SALES; T36 moved its "read a real compliance rule" probe from SALES to MD. Confirmed against 002: `compliance:rule:read` is held by OPS/FINANCE/MD/ADMIN only — SALES is genuinely absent, so both amendments reflect 021's intended behavior change, not a masked regression.

**3. R18 executor.** `app.check_opportunity_stage_move` is called once at `resolve_action_target_id` (request time) and again inside `execute_in_database_action` under `FOR UPDATE` on the opportunity row — the second call's `SELECT stage INTO v_current` runs after the lock is taken, so `fromStage` is compared against a value read inside the lock, not before it. Cross-tenant: `resolve_action_target_id` resolves the target id with `WHERE tenant_id = p_tenant_id AND ref = p_target_ref`; a ref from another tenant resolves to no row, and the executor's `UPDATE` is additionally scoped `WHERE tenant_id = v_request.tenant_id`. Case/whitespace bypass: the target `stage` is matched against `core.pipeline_steps.step_key` by exact text equality before any approval routing is evaluated, so a variant that doesn't exactly equal a configured step key (`WON`, `LOST`, …) fails `UNKNOWN_STAGE` and never reaches the OPP-01 policy match or the enum-typed `UPDATE` — verified empirically (Teeth 2). `fromStage` uses `IS DISTINCT FROM`, so a client omitting it or sending a wrong case is `STAGE_MOVED`, fail-closed either way.

**4. Tenant trigger.** `app.seed_opportunity_stage_policy` inserts with `ON CONFLICT (tenant_id, id) DO NOTHING` — idempotent, re-running it (trigger fire or backfill re-run) only inserts missing rows. `public.tenants` grants `authenticated` only `SELECT`/`UPDATE` (014:1175-1176), no `INSERT`, so a client cannot fire the `AFTER INSERT` trigger. The backfill (`SELECT app.seed_opportunity_stage_policy(tenant.id) FROM public.tenants`) runs over every tenant but is a no-op for tenants that already have OPP-01 — `$verify$` V4c independently re-asserts every tenant has the policy row after the backfill.

**5. Rollback.** `supabase/rollbacks/021_golden_path_authz_rollback.sql` §2 counts live rows across 8 tables (`action_requests`, `approval_requests`, `autonomy_grants`, `suggested_drafts`, `routing_entries`, `jury_configs`, `hours_saved_baselines`, `evals`) filtered on `action_type = 'OPPORTUNITY_STAGE_CHANGE'` and raises before deleting anything if any count is nonzero. Otherwise it restores 001–020's catalog (24 functions from 018, `get_audit` from 020, three 011 dispatch functions, 019's `seed_pipelines`), each reproduced in full, not referenced.

**6. Executed on the shim.** See table above — 22/22 migrations, 10/10 pin, both teeth checks behaved as expected (one caught a real regression, one confirmed no bypass).

**7. `npm run lint:sql`.** Fails because `scripts/check-sql-parse.mjs` globs every file under `supabase/seeds/*.sql` (line ~32 of that script) and parses each with `libpg-query`, which has no grammar for psql meta-commands — `supabase/seeds/test_hosted_demo.sql` uses `\ir hosted_demo_akademi_perdana.sql` / `\ir hosted_demo_wipe.sql` (lines 62, 228, 257) to include sibling files, which is not valid standalone SQL.
