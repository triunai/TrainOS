## 2 · Fix (a): "CLIENT exempt while `app.role_permissions` has no CLIENT row". Judgement: **a latent hole, HIGH**

### 2.1 What it does, executed

Probe `probe_a_client.sql`: `test_011` in full, then one-statement probes, then `ROLLBACK`. Database `rv13_full`,
001–017. Claims used: `{"app_role":"CLIENT","actor_kind":"CLIENT","aal":"aal1"}`, which is exactly what
`app.principal_claims` (`002:532-567`) emits for a `memberships` row with `role = CLIENT, actor_kind = CLIENT`.

| Probe | CLIENT principal | HUMAN SALES control |
|---|---|---|
| `ENQUIRY_ARCHIVE` (no policy row) | `EXECUTED` 202 | not a useful control: SALES holds `enquiry:archive` (scope-narrowed), so it would pass |
| `QUOTATION_APPLY` (money-moving) at aal1 | **`EXECUTED` 202** | `AAL2_REQUIRED` |
| `AGENT_PAUSE` | **`EXECUTED` 202** | `FORBIDDEN agent:pause` |
| `BUDGET_CAP_RAISE` | reached policy FIN-07, queued for MD (failed only on no eligible approver) | n/a |
| `authenticated → core.perform_action('ENQUIRY_ARCHIVE')` | `{"success":true,"data":{"status":"EXECUTED"}}` | n/a |

Ledger after the probes: `core.action_requests` rows with `requested_by_kind = CLIENT, status = EXECUTED`, and
`ENQ-T011-4` / `ENQ-T011-5` `ARCHIVED`. The log is `out/rv13_full_probe_a_client.sql.log`.

Two mechanisms combine:
- `011:2323-2326` skips the permission check for CLIENT.
- `011:2371` applies the H-05 AAL2 gate to `HUMAN` only.

Dispatch at `011:2651-2662` then sends any CLIENT request with no matching policy straight to `EXECUTING`. That
covers `ENQUIRY_ARCHIVE`, `OPPORTUNITY_CONVERT`, `TNA_RECOMMENDATION_ACCEPT` and `AGENT_PAUSE` (GOV-02 is never
gated), plus conditional types whose conditions miss: `PAYMENT_RECORD` when the amount matches, `DISCOUNT_APPROVE`
above floor, `QUOTATION_APPLY` within authority.

This is T3 ("no permission check, dispatch falls through to EXECUTING") reopened for a whole principal kind, with
MFA also off. It contradicts 011's own `COMMENT ON COLUMN app.action_types.required_permission` (`011:2111-2115`):
"The app.role_permissions key a HUMAN or CLIENT actor must hold".

### 2.2 The pin does not pin it: teeth-check (a) FAILS in both directions

T17e's CLIENT fixture (`test_011`, just above `DO $t17$`) is
`{"app_role":"MD","actor_kind":"CLIENT"}`. MD holds `enquiry:archive`, so `has_permission` is true whether or not
CLIENT is exempt.

| a1: `IF v_actor_kind IN ('HUMAN','CLIENT')` (the pre-fix gate, no exemption) | **19/19 PASS**; T17 PASS | `out/teeth_a1_client_gated_unconditionally_MUTATED.log` |
| a2: `… AND false` (exempt forever, conditional removed) | **19/19 PASS** | `out/teeth_a2_client_exempt_forever_MUTATED.log` |

To confirm a1 really gated CLIENT, I re-applied a1 and ran the probe with `app_role: CLIENT`. Every CLIENT probe
was refused `FORBIDDEN requiredPermission=…` (`out/teeth_a1_confirm_probe.log`), while `test_011` in the same file
still passed T17. So the mutation took effect and the pin could not see it.

### 2.3 What happens the moment someone seeds one CLIENT permission

I executed this as `probe_a3_seeded.sql`: `INSERT INTO app.role_permissions VALUES ('CLIENT','quotation:apply')`,
then the same probes.
- `ENQUIRY_ARCHIVE`, `DISCOUNT_APPROVE`, `AGENT_PAUSE` and `BUDGET_CAP_RAISE` flip to `FORBIDDEN`.
- `QUOTATION_APPLY` still executes, **at aal1**, because the AAL2 gate is HUMAN-only.

So the switch-on is correct, automatic and fail-closed. Seeding is not the danger. Three residues remain:
- `app.role_permissions` has no `tenant_id` (`\d`: `role, permission`). One seed flips the gate for every tenant at
  once. That is fine, because it fails closed, and `authenticated` holds no privilege on the table, so only a
  migration can seed it.
- T17e0 turns into a tripwire that fails the pin on seed, by design.
- Nothing pins that the gate actually switches on (a2 above).

### 2.4 Reachability, and why HIGH rather than CRIT

- `public.memberships.actor_kind` accepts `CLIENT`. The only CHECKs are the agent/agent_id pairing, agent role,
  status and trainer_id, per `pg_constraint`. Nothing ties `CLIENT` to anything.
- `memberships_write_admin` (`002:750`) lets any tenant ADMIN at aal2 insert one. `authenticated` holds
  `INSERT, UPDATE` (`014:1179`).
- The access-token hook copies `actor_kind` into the JWT (`002:561`).
- Guard a (`011:2199-2218`) stops `p_requested_by` from manufacturing CLIENT, so the JWT is the only source.

**No code path creates a CLIENT-kind membership today.** `grep` over `apps/`, `packages/`, 014–017 and
`origin/lane/rpc-018` found none; 018 uses `actor_kind = 'HUMAN'` branches and `emit_event` for portal writes.

So the hole is data-gated behind one ADMIN-created row, not open to any caller today. That is why it is HIGH and
not CRIT. It blocks for three reasons:
1. It is an authorization fail-open on money-moving actions for an external principal kind.
2. The fix's own comment (`011:2300-2308`) expects CLIENT callers to arrive with 018's portal path.
3. The pin actively enforces "CLIENT performs a staff action". Closing the hole makes the intent visible, but
   nothing currently catches it.

The re-review graded the mirror-image latent case (CLIENT always refused) HIGH. Consistency requires the same grade
for the fail-open version, which is strictly worse.
